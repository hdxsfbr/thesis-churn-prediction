## What was built

`orchestration.lock` takes the `cycle` row with one MERGE. The update matches only when the holder is already us or the heartbeat is older than `ttl_s` (300 seconds). A live holder makes `run_cycle` return `SKIPPED` and write no `RUNS` row. The lock is released when the call returns, including when the call raises.

`V020__run_steps_locks.sql` adds `RUN_STEPS` (`run_id`, `step`, `shard`) and `RUN_LOCKS`. A cycle that died `FAILED` or is still `RUNNING` skips a `write_scores` shard or an `agent` shard that is already `done`. A `SUCCEEDED` replay runs the steps again. Writes stay MERGE / insert-only, so the replay does not add rows.

`count_active` retries `SourceUnavailable` three times, then the run fails and no scores are written. The next call, with the source back, finishes the run.

`shards` defaults to 1, and that path still writes scores in one transaction. Above 1, each score shard and each agent shard commits on its own. A failed shard is not marked done, and a resume does not delete the shards that are. The agent shard deletes coverage gaps only for its own keys.

`FaultyWarehouse` fails source reads, fails one `RISK_SCORES` merge, and exposes `before_step` so a test can stop the cycle on a named step.

## Deviations

- The migration is `V020`, not `V012`. `V012` was never merged. The next free number after `V019` is `V020`. `V013` stays reserved for the sender view.
- Resume looks at the previous `RUNS` status. `SUCCEEDED` is a replay, not a resume. The replay still executes `validate`, so a patched failure on a second call still clears the success counts. Insert-only writes keep the first log and outbox rows.
- The score write for `shards=1` is unchanged: one transaction, and a count mismatch rolls the delete and the merge back together. The checkpoint is marked only after that transaction commits.
- DuckDB uses one connection. The concurrent test holds the lock row. It does not open a second connection.
- `validate` reads `information_schema`, not the source tables. The retried read is `count_active`, whose SQL names `THESIS_SYNTH`.
- An `LLMError` raised from `before_step` is outside the template fallback, so that agent shard fails. The next call keeps the shard that finished and completes the rest. Stored `content_ref` values on the finished shard do not change.
- `SystemExit` between `agent` and `outcomes` leaves `RUNS` at `RUNNING` and the agent checkpoint done. Python still runs the lock's `finally`, so this test does not leave a stale lock. Stale takeover is the other test.

## Proposed ARCHITECTURE notes

- `RUN_STEPS` and `RUN_LOCKS` are `V020`. `V012` is an unused hole and stays unused.
- The lock MERGE updates the row only for the same holder or a heartbeat older than `ttl_s`. Otherwise `run_cycle` returns `SKIPPED` and does not write `RUNS`. Default ttl is 300 seconds. The same call releases the lock on the way out.
- Checkpoints skip completed `write_scores` and `agent` shards only when the previous status is `FAILED` or `RUNNING`. A successful replay runs again. Insert-only keys are what keep the replay identical.
- `shards` defaults to 1. The single score write stays one transaction. More shards commit independently and a resume does not delete a shard that is already done.
- Source retries are three attempts on `SourceUnavailable`, then `FAILED` with no score rows. The read that hits the source is `count_active`.
- A checkpointed recovery on the synthetic warehouse is not a live process kill and not a live Snowflake outage.
