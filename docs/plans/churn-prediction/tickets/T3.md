## 3. Design conformance (ARCHITECTURE §3, §4.2)

The build matches the approved design, so ARCHITECTURE.md was **not** edited:
- The module layout is `contract/loader.py`, `contract/validate.py` and `contract/views.py`, as §3 lists. `validate` moved out of `loader.py`. `contract/__init__.py` re-exports it.
- `validate` runs at the start of the cycle and fails with `ContractError` before writes. The CTEs apply renames, UTC normalisation and QUALIFY dedup. KEY_MAP sits in a separate `CHURN_PRIVATE` schema.

These points are known and are not gaps for T3's requirements:
1. **Pepper as a literal, not a bind.** §4.2 shows `SHA2(:pepper || customer_id, 256)`. The code inlines the pepper as an escaped SQL literal (unchanged from T1). The key value meets R7.1. The exposure in Snowflake QUERY_HISTORY is a hardening item for T25 (PII hardening). The design is not changed to match.
2. **Key-map source.** §4.2/§10 foresee a `customers_pii` contract view feeding the key map. That view does not exist yet. For now `key_map_frame` builds the map from every contract view that carries `customer_id`. When `customers_pii` is added, it is picked up automatically, because it carries `customer_id`.
3. **KEY_MAP grants** (only `CHURN_SENDER` and `CHURN_APP` may read it) are a Snowflake deployment concern (T23/T25). V003 and `docs/data-contract.md` say so.

These come from code review, are non-blocking and are not requirement gaps:
- `CHURN_CONTRACT_PATH` takes precedence over an explicit `overrides={'contract_path': ...}`. `CHURN_DUCKDB_PATH` behaves the other way. Neither is tested.
- Dedup has no tie-breaker when two rows share an id and the same `loaded_at`.
- On Snowflake, `timestamp_tz` mapped onto a TIMESTAMP_NTZ column would be read in the session time zone.
