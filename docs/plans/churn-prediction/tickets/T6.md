## 1. Requirement trace

### R3.2 Explainability

*Requirement (PRD):* each score comes with its top contributing factors, each with a direction and magnitude, in human-readable form.
*Design (ARCHITECTURE §6.3, TASKS T6):* LightGBM `pred_contrib=True` gives per-feature log-odds contributions plus a bias. The top-k by |contribution| (k=5, at least 3 when enough features are non-missing) are rendered as `{feature, label, direction, contribution, value}` through registry label templates. Scoring writes them to `RISK_SCORES.top_factors`. Contributions plus bias equal the raw margin to within 1e-6, and the signs match the direction labels.

## 3. Design conformance and document changes

- **Matches §6.3.** The change uses `pred_contrib` contributions, k=5 with a minimum of 3, ranking by |contribution|, registry templates, and the `{feature, label, direction, contribution, value}` shape. Isotonic or sigmoid calibration is monotone, so the directions computed on the margin still hold for the calibrated probability.
- **Storage type of `top_factors` (ARCHITECTURE §5.3 clarified).** The design says "array of {…}". The build stores that array as JSON text in a `VARCHAR` column, which works the same on DuckDB and Snowflake. This is the same logical structure, not a contradiction, so I made a clarification rather than reporting a gap. I edited the §5.3 `RISK_SCORES` row to say the column is JSON array text added by V014, and that readers (T13 rationale, the INTERVENTION_LOG writer) must `json.loads` / `PARSE_JSON` it.
- **Migration number.** TASKS.md plans versions up to V013 for other tickets, and T12 owns V006. T6 takes V014, so nothing collides. TASKS.md is unchanged (ticket runs do not edit it).
- **Project docs.** `README.md` is still the GitLab template and does not describe the pipeline yet. `docs/output-tables.md`, which §9 cites for R3.5, does not exist yet (it belongs to a later ticket). So no project doc became out of date because of this change, and none was edited.
