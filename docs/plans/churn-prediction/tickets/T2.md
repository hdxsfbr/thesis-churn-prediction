### R1.2 Realistic, full-scale synthetic data

*Requirement:* historical cancellations so that precision and recall can be measured; volume at least the scale of the active base (A5: about 350k subscribers in total, ≥7.5M quiz rows); edge cases: no quiz, no email, no tickets, partial records, nulls, duplicates, late-arriving rows. ARCHITECTURE §5.2 adds single order, tenure < 30 d and timezone offsets, and the data profile is the R1.2 acceptance artefact.

## 2. Design conformance (ARCHITECTURE.md)

The built design matches ARCHITECTURE §5.2 items 1–5, and ARCHITECTURE.md was **not** edited. Some details are not spelled out in the design, but none of them contradicts it:

- `THESIS_SYNTH.latent_truth` stores the true archetype per customer. It is needed to judge the archetype model against the latent archetype (PRD A3). It is **not** in `source_contract.yaml`, so the pipeline cannot read it through the contract. Later tickets must keep it out of the contract.
- `tz_offset_min` is a new contract column on `email_events` and `support_tickets`. Per §5.2 item 3, the contract CTEs normalise these timestamps to UTC. That normalisation, and documenting the column in `docs/data-contract.md`, belong to T3 (contract hardening). Until T3, the views expose local wall-clock time on about 5% of email/support rows.
- The new tables use additive migrations at the next version numbers (`sql/synth/V002`, `sql/migrations/V002`), following the T1 convention.

## 3. Observations (non-blocking, for later tickets)

1. `generator._subscription_events`: the `PAYMENT_FAILED` dunning events (`cancel_day - 14/7`) and the current-state `PAUSED` / `PAST_DUE` events (`total_days - uniform(...)`) are not clamped to `start_day`, so for very recent or very short subscriptions a few events can come before the subscription starts. T4 features should clamp or filter these, so tenure is never negative (code review note 1).
2. `profile.py` has some unused or duplicated code (`ROW_LEVEL_TS`, `DEDUP_VIEWS`, `DataProfile.extra`). It does not affect any requirement.
3. The checked-in `.venv` has no python binary. Tests were run from a separate venv.
4. `README.md` is still the GitLab template. A project README is outside T2's files (deployment docs come later), so it was left alone.
