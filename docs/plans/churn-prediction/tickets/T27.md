## What was built

`generate` still builds tiny and small (at or under 40,000 customers) in one draw, so those populations do not move. `full` and `default` are 350,000 customers. Above one chunk the generator deletes the source tables, then writes each 40,000-customer range in its own transaction. Event ids are prefixed with the chunk origin so rows from different chunks do not collide. Archetypes are slices of the one `draw_archetypes(seed, n)` array, so `latent_archetypes(scale="full")` still matches `latent_truth`.

`churn cycle --timed` copies that run's `RUNS.duration_s` into `CHURN_OPS.RUN_METRICS` (`metric = duration_s`). The runner already stores the duration on `RUNS` for every cycle.

## Deviations

- `config/settings.yaml` is not on the T27 file list. `full: 350000` is the scale the tests select. `default` stays 350,000.
- `sql/migrations/V018__run_metrics.sql` is not on the file list. `RUN_METRICS` did not exist, and the timed cycle has to write a row. V017 is the highest migration on main. The table is `(run_id, metric, value, recorded_at)`. T19 adds the other metrics to this table.
- A chunk does not replay the single-stream RNG of a monolithic 350,000-customer draw. The first chunk uses the original seed. Later chunks use a seed mixed with their origin. Tiny and small never take this path.
