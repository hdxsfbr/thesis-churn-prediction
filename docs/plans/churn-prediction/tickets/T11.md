## 2. Design conformance

The built types match ARCHITECTURE §6.4 step 4 and §6.5 (escalation on `human_queue`). One naming change, which I made in ARCHITECTURE.md:
- **§6.4 step 2**: the cost method is `cost_usd(context)` (base default 0.0), not `cost(context)`. It is the same design under the unit-explicit name the gate (`cost_usd ≥ T_cost`, A6) uses. Nothing else in ARCHITECTURE.md changed.

These are interim states that later tickets complete by plan, not design changes:
- **Context fields are not filled from data yet.** `has_quiz`, `quiz_goals`, `recommended_sku`, `top_blend_goal` and `goal_email_engagement` default to "unknown". `max_discount_pct` and `offer_catalogue` default to the A6 values and are not yet read from the run's config snapshot in `cycle.py`. Filling them from features and the config snapshot belongs to T12 (guardrails) and T13 (policy). `cycle.decide` still picks `checkin_email` only until T13. R4.1 and R4.3 are about the types producing valid actions from suitable profiles, and that is proven.
- **`eligible(context)`** (§6.4 step 2) is not declared by the types yet. It arrives with guardrails in T12.
- **All-above-cap clipping**: when every catalogue entry is above the cap, the offer keeps its code (e.g. `PCT_25_NEXT_2`) with a smaller `discount_pct`. That matches "clipped or blocked" in §6.4 and the ticket's "clip" wording. T12 may choose to block such entries instead.
- **Offer economics** (`OFFERS` table of discount, cost and uplift, `VALUE_USD = 120`) are module constants. The policy priors and tenure value from runtime defaults arrive in T13.
