## 1. Requirement trace

### R3.4 Risk tiers set in configuration

*Requirement:* subscribers go into risk tiers whose boundaries are set in configuration. *AC:* changing a tier boundary in configuration changes the tier assignment on the next run, with no code change.

| Aspect | Implementation | Test |
|---|---|---|
| Boundaries live in configuration, with A6 defaults | `config/runtime_defaults.yaml` `tiers.boundaries` = medium 0.20 / high 0.45 / critical 0.70, `at_risk_from: medium`. `churn bootstrap` (`src/churn/cli.py::bootstrap`) runs `runtime_config.seed` into `CHURN_OPS.AGENT_CONFIG` (`sql/migrations/V004__runtime_config.sql`). | `test_runtime_config.py::test_defaults_are_valid` |
| Bootstrap keeps edits made in Metabase | `seed(..., overwrite=False)` does a MERGE with `insert_only`. `--reset` overwrites. | `test_runtime_config.py::test_seed_preserves_edits` |
| Tier assignment from boundaries | `runtime_config.assign_tiers`: each boundary is the inclusive lower bound of its tier. `src/churn/model/score.py::score_frame` writes `RISK_SCORES.tier` (column added by V004) from the run's config. | `test_runtime_config.py::test_assign_tiers_boundaries` (edges 0.2 / 0.45 / 0.7) |
| AC: edit the config, next run re-tiers, no code change | `runner.run_cycle` calls `load_pinned` at the start of every run. ### R5.2 No-code thresholds (mechanism)

*Requirement:* thresholds can change without code changes or redeployment. The routing AC ("changes the routing on the next agent run") needs the gate and agent, which arrive in T14 (TASKS.md: "R5.1–R5.4 → T14 (R5.2 mechanism in T5)").

| Aspect | Implementation | Test |
|---|---|---|
| Thresholds in a runtime table, with A6 defaults | `gate` row in AGENT_CONFIG: `t_risk` 0.85, `t_cost_usd` 15, `t_discount_pct` 20, `always_approve` []. `GateConfig` is validated by pydantic. | `test_defaults_are_valid` |
| Re-read at every run, no redeploy | `runtime_config.load` reads AGENT_CONFIG and `load_pinned` runs at run start, inside `run_cycle`. | `test_seed_preserves_edits` (an edited gate is read back). The same per-run reload is proven for tiers by `test_changing_boundary_changes_tier_next_run`. |
| Pinned per run, rerun reuses it (A12, ARCH §4.3, R8.2) | `load_pinned` returns the existing `CONFIG_SNAPSHOTS` row for the run id, or validates and MERGEs a new one. `RUNS.config_snapshot_id` = run_id. | `test_tier_config_change.py::test_rerun_reuses_pinned_snapshot`: after an edit, a rerun of the same id has an identical snapshot JSON and identical tiers, while a new id picks up the edit |

### PRD §7 Threshold configuration missing or invalid → fail safe

*Requirement:* the system must fail safe (route to approval or halt), never act autonomously. ARCH §4.3: invalid gate → `approve_all`, run DEGRADED, `ConfigError`. Invalid tiers or guardrails → the agent step halts and scores are still written.

| Aspect | Implementation | Test |
|---|---|---|
| Invalid gate thresholds → `approve_all`, DEGRADED, ConfigError | `runtime_config.parse` never raises. A failed `gate` section sets `gate_mode="approve_all"`. `run_cycle` writes RUNS `status=DEGRADED`, `error_class=ConfigError` and the error list in `error_msg`. `RunResult.gate_mode` carries the mode to the agent step (T14). | `test_runtime_config.py::test_invalid_thresholds_yield_approve_all_and_degraded`, run with out-of-range, wrong-type, negative and malformed-JSON values. It checks RUNS, CONFIG_SNAPSHOTS (`valid` false, `gate_mode`) and that scores are still written. |
| Invalid tiers or guardrails → agent halt, scores still written | A failed `tiers` / `guardrails` (or `holdout` / `outcomes`) section sets `agent_halt=True`. This is exposed as `RunResult.agent_halted` and `CONFIG_SNAPSHOTS.agent_halt`, and the run is DEGRADED. Scoring still runs. | `test_runtime_config.py::test_invalid_tiers_or_guardrails_halt_agent`: 3 tier cases and 3 guardrail cases (cap 0, empty catalogue, garbage). `scored == active_in_source > 0`. |
| Missing keys → fail safe, never silent defaults | A missing key or NULL value counts as an error for its section. An empty table gives `approve_all` plus halt. The YAML defaults are used only by `bootstrap`, never as a run-time fallback. | `test_runtime_config.py::test_missing_keys_fall_back_failsafe_not_autonomous`: gate missing, guardrails missing, and an empty table, end to end |
| Config table unreadable | An exception in `load_pinned` (inside the `try` block) makes the run FAILED and raises `RunFailed`. Nothing is scored autonomously. | Covered by reading the code only. No dedicated test; the ticket does not require one. |

## 2. Documents updated

- `ARCHITECTURE.md` §3 and §4.3 now describe the design as built. None of these changes contradicts the approved design, and each is a refinement inside it:
  - the module is `churn.runtime_config` (`load_pinned`), not `settings.runtime.load()`, as the TASKS.md file list already said
  - `CONFIG_SNAPSHOTS` has extra columns (`gate_mode`, `agent_halt`, `created_at`)
  - the config has five sections; missing or invalid `holdout`/`outcomes` also halt
  - a halt run is also DEGRADED / ConfigError
  - invalid tiers leave `tier` NULL
  - invalid snapshots are pinned too
  - `bootstrap` keeps edits and `--reset` overwrites them
- README.md is still the GitLab template, and there is no operator guide yet (T28 owns the README and docs). No other project document describes runtime config, so none needed updating.
- I did not touch TASKS.md or WAVES.md.

## 3. Notes and follow-ups (non-blocking)

- `tests/conftest.py` was edited outside the listed files: the shared `pipeline` fixture now seeds AGENT_CONFIG. Without that, every run would be DEGRADED. This is justified.
- The agent-side effects of `gate_mode` and `agent_halt` (no outbox rows, agent step skipped) are enforced by T10 and T14, which consume `RunResult` and the snapshot. T5 provides and tests the flags and run status, which is the TASKS.md scope ("mark the agent step to halt").
- Code-review suggestions for later tickets:
  - duplicate `key` rows in AGENT_CONFIG are resolved non-deterministically
  - `extra='forbid'` would catch typos in optional fields
  - `GateConfig` accepts `Infinity` values
  - the `settings` argument of `defaults()` is unused

  None of these breaks a T5 requirement. The PRD §7 fail-safe holds for every case that is tested.
- "Tests written to fail first" rests on the builder's report and cannot be checked from the tree.
