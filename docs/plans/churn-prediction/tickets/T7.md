## 1. Requirement trace

### R3.3 Archetype classification

*Requirement (PRD):* each at-risk subscriber gets one primary archetype from {price sensitivity, efficacy dissatisfaction, subscription fatigue, life change}, with a confidence value.

*AC:* every at-risk score row has an archetype and a confidence. The archetype evaluation report shows per-archetype precision against the chosen ground truth. The report part belongs to T8.

*Design (A3, §6.3, TASKS T7):*
- Weak labels come from cancellation reason codes and ticket categories, mapped in `config/archetype_labels.yaml`.
- A multinomial logistic regression over standardised features is trained on weak-labelled churned snapshots.
- It outputs probabilities, the argmax and the confidence, plus a low-confidence flag (`max_prob < 0.40` or `top1 - top2 < 0.10`).
- On synthetic data it is judged against the generator's latent archetype.

## 3. Documentation changes made in this run

- **ARCHITECTURE §5.3 `RISK_SCORES`**: added `archetype_low_conf` (boolean), the format of `archetype_probs` (JSON object text), and the migration `V007__risk_scores_archetype.sql`. The design already defines the flag in §6.3; the table row did not list it as a column. This is additive and does not contradict the design.
- **ARCHITECTURE §6.3 "Archetype"**, as-built notes:
  - The classifier lives in `bundle["archetype"]` and uses an imputer, a scaler and a class-balanced, seeded logistic regression.
  - The thresholds are module constants (`MIN_CONF`, `MIN_MARGIN`), not `settings.yaml` keys. The values match the design.
  - The weak-label precedence is: the reason code first, then the majority ticket category with a deterministic tie-break.
  - Every scored row is classified, which is a superset of the at-risk rows.
  - With fewer than 20 labelled churners, or only one class, no classifier is fitted and the columns are NULL.
- The README is still the GitLab template, and no project doc under `docs/` describes `RISK_SCORES` or the model bundle. Neither needed a change.
- I did not edit TASKS.md or WAVES.md, as the ticket-run rule requires.

## 4. Out-of-slice change and follow-ups (not blocking)

- **Interim latent archetype in the generator** (`synth/latent.py`, `synth/generator.py`):
  - What was built: a categorical latent archetype from its own RNG stream (shares 0.35 / 0.25 / 0.25 / 0.15). It sets the cancellation reason code with 25% noise ("OTHER" included), which matches §5.2. It also adds a discount boost for price-sensitive customers, a refund boost for efficacy-dissatisfied ones, and a wind-down cadence stretch (fatigued ×2, life_change abrupt).
  - Where it differs from §5.2: §5.2 gives refunds to price-sensitive customers and has fatigued customers skip orders and lose email engagement. There are no support tickets yet.
  - Status: the operator accepted this interim change in T7 at code review, and T2 (the owner of §5.2) will reconcile it. I did not edit §5.2 because the full generator design still stands for T2.
  - When T2 lands, re-run `test_archetype_beats_chance_on_latent_truth`: life_change precision is about 0.26 against the 0.25 threshold.
- **Precision population**: the precision test judges all scored subscribers, because the tiny fixture has about 10 at-risk rows. TASKS only asks for precision above 0.25 on synthetic data, so the test satisfies it. Narrow the test to at-risk rows once the fixtures are larger.
- **NULL fallback**: when no classifier can be fitted (fewer than 20 labelled churners), at-risk rows get NULL archetype columns. This cannot happen at the fixture or A5 scales, but T13's low-confidence or escalation handling should treat a NULL archetype as low confidence.
