## What was built

Three intervention-history features are computed from `INTERVENTION_LOG` for each `as_of`. `n_interventions_90d` counts dispatched actions in the last 90 days. `days_since_last_intervention` is the recency of the latest one. `last_intervention_type` is that action encoded as a number: check-in 1, formulation 2, retention offer 3, escalation 4. Holdout rows are not contacts. When the ops log table is absent, the three features are 0 or NULL and the query still runs.

A closed treated outcome replaces the cancellation label on a training snapshot. Churned becomes 1 and retained becomes 0, using the latest outcome measured at or before the snapshot.

`churn retrain` fits a candidate, scores it and the promoted model on the same time holdout, and promotes the candidate only when top-decile precision and PR-AUC are each at least the current model's minus `retrain.tolerance` (0.01). Otherwise the candidate is stored as `rejected` and the current model stays promoted. Both results record the metrics and the reason. `churn train` still promotes the first model with no comparison.

`retrain_due` is true when more than `retrain.min_new_outcomes` (100) closed treated outcomes have been measured since the promoted model. The weekly cron remains the scheduler's. The CLI runs a retrain whenever it is called.

## Deviations

- `config/settings.yaml` and `Settings` gained a `retrain` section. Without that field the yaml values would be dropped.
- `sql/features/subscriptions.sql` and `features/builder.py` grew the master query. `interventions.sql` alone cannot add columns to the feature frame. The builder substitutes an empty CTE when `INTERVENTION_LOG` does not exist, which is the hand-built feature fixture.
- `docs/features.md` was regenerated from the catalogue. The drift test requires it.
- `model/train.py` sorts each fit by snapshot and subscriber and reseeds before fitting. A second fit of the same rows should not depend on whatever random state an earlier test left behind.
- On the tiny holdout, top-decile precision moves by one row at a time, and that step can be larger than 0.01. A refit of the same data can therefore be rejected even though the ranking barely moved. The rejection is recorded and the current model stays promoted. The tolerance itself is the unit test, on exact numbers.
- No new migration. `MODEL_REGISTRY` already stores status, reason, and metrics.
- The schedule string `schedule.retrain_cron` is not read here. T22 owns the worker.

## Proposed ARCHITECTURE notes

- Intervention history is three features on the existing frame, not a new table. The type is the code in `INTERVENTION_TYPE_CODE`. Holdout is excluded. A missing ops log yields the missing-data policy (count 0, recency and type NULL).
- A closed treated outcome measured at or before the snapshot replaces the voluntary-cancellation label for that subscriber. Churned is 1, retained is 0.
- `churn retrain` writes `retrain-YYYYMMDD-<fingerprint>`. Promotion requires both holdout metrics to be at least the current model's minus `retrain.tolerance` (0.01). A rejection keeps the promoted row and stores the candidate as `rejected` with the metrics and the reason. `churn train` is still the unguarded first promotion.
- `retrain.min_new_outcomes` defaults to 100. `retrain_due` is the count of closed treated outcomes after the promoted model's `created_at`. The cron stays with the scheduler.
