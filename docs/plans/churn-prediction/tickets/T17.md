## What was built

`feedback.policy_stats` rebuilds each `(archetype, intervention, bucket)` Beta posterior from the configured prior plus every closed treated outcome. A retained outcome adds one to alpha. A churned outcome adds one to beta. `unknown`, holdout, and anything that was not `DISPATCHED` are left out. The bucket is the `tier:tenure` value already stored on `policy_scores`.

The rebuild is the whole history, oldest outcome first. Calling it again on the same rows writes the same alpha, beta, and `n`. `policy.decay` defaults to 1, which keeps every outcome at full weight. A smaller decay multiplies the running posterior before the next outcome.

`run_cycle` runs `policy_update` after `outcomes`. The decide step has already loaded `POLICY_STATS`, so this run keeps those posteriors. The write is what the next run reads. The stored alpha and beta include the prior, because selection uses a table row in place of the prior.

## Deviations

- No new migration. `POLICY_STATS` already exists (`V016`). Idempotency is the rebuild, not a ledger of decision ids.
- `policy.decay` is an optional field on `PolicyConfig`, default 1. `runtime_defaults.yaml` is unchanged; a missing decay means no decay.
- The shift test flattens the efficacy priors for formulation and check-in to `(20, 20)`. The shipped priors already prefer formulation for efficacy, so they cannot show a share that rises because of new outcomes. Two waves of seeded rows retain formulation 80% of the time and check-in 20% of the time. Formulation's selection share is higher after the first wave than under the flat prior, and higher again after the second wave.
- Control churn is not subtracted inside the posterior. That stays a reporting concern, as ARCHITECTURE §6.6 already says.

## Proposed ARCHITECTURE notes

- `policy_update` runs after `outcomes` and after `decide`. This run's selections keep the `POLICY_STATS` rows loaded at decide time. The next run sees the rebuild.
- A stored posterior is the configured prior plus treated evidence, not the evidence alone. `select` uses the row in place of the prior. Holdout, `unknown`, and rows that are not `DISPATCHED` do not enter it.
- Rebuilding from the log is what makes a second apply a no-op. There is no applied-decision ledger and no new migration.
- `policy.decay` defaults to 1. Values below 1 shrink the running posterior before each next outcome, oldest first. The bucket is read from `policy_scores`, key `bucket`.
- The shipped efficacy prior already prefers formulation. A shift test has to start from a flatter prior, or the 80/20 seed cannot show a rising share.
