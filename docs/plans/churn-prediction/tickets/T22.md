## What was built

`churn worker` catches up today's scheduled cycle when that run is missing or not `SUCCEEDED`/`DEGRADED`, then blocks on an APScheduler `BlockingScheduler`. The daily job is `schedule.cron` (`0 6 * * *`, UTC). The weekly job is `schedule.retrain_cron` (`0 6 * * 1`, UTC).

The daily job calls `run_cycle` with kind `scheduled`, so the run id is `scheduled-YYYYMMDD`. The agent in that cycle reads the scores just written for the same run id. The weekly job calls `retrain`. A daily cycle also retrains when `retrain_due` is true. Until T18 is on the branch that import is absent, and the daily call does nothing.

A second catch-up on a finished run id does not start another cycle.

## Deviations

- `schedule` is a settings block. Without it, pydantic would drop the cron strings and the worker would not see them.
- `apscheduler` is pinned to `>=3.10,<4` so `BlockingScheduler` and `CronTrigger.from_crontab` stay the API the worker uses.
- Tests fire `Worker.cycle` through a stand-in clock. They do not call `scheduler.start()`, which would block.
- The retrain callable is imported lazily. This branch is stacked on T21 and does not contain T18 yet.

## Proposed ARCHITECTURE notes

- `schedule.cron` is `0 6 * * *` UTC. `schedule.retrain_cron` is `0 6 * * 1` UTC. Both are read from settings, not hardcoded in the job.
- Catch-up runs once when today's `scheduled-YYYYMMDD` row is missing or not `SUCCEEDED`/`DEGRADED`. A finished row is left alone.
- The daily job is the cycle. The agent scores and decisions share that run id. The weekly job is the retrain. A daily cycle retrains only when `retrain_due` is true.
- The lock inside `run_cycle` is what keeps a second worker from overlapping the same day.
