## 3. Operator decisions (2026-10-21)

**D1, expiry vs R5.3 AC. Code change, rework.** ARCHITECTURE §6.5 expired only rows still PENDING past `expires_at`. As built, expiry is judged on the processing time, so an approval given just before the 72 h deadline but processed by the next daily cycle became EXPIRED. That breaks the R5.3 AC. The operator chose: *add a configurable grace period after the deadline for answered rows. Default it to one daily cycle (24 h), keep it in the runtime config, judge it on processing time (not the editable decided_at), and add a test for an approval made in the last hours before the 72 h deadline producing exactly one outbox row on the next cycle.* ARCHITECTURE §6.5 and A6 now describe this.

**D2, approval re-check scope. Documents only.** §6.5 asks the APPROVED re-check to cover contact cap and email unsubscribe as well. Those rules come with T12 (wave 7), so T14 checks only "still active". The operator accepted this. T12 must add the contact-cap and email-unsubscribe re-check for APPROVED rows at execution, with a test. This is recorded in ARCHITECTURE §6.5 and here. The operator also decided that the matching T12 entry in TASKS.md is edited at plan level later, because ticket runs do not edit TASKS.md.

## 4. Rework instructions for the Builder (D1)

1. `src/churn/runtime_config.py::GuardrailConfig`: add `approval_grace_h: float = Field(default=24, ge=0)`. `config/runtime_defaults.yaml` → `guardrails.approval_grace_h: 24`.
2. `src/churn/execution/approvals.py::process`: take the pinned config (or the grace value) from the runner. Keep the trusted deadline `INTERVENTION_LOG.approval_expires_at` and judge everything on `now` only. Never use `APPROVALS.expires_at` or `decided_at` for expiry.
   - PENDING or invalid value: EXPIRED when `now ≥ deadline` (unchanged).
   - APPROVED or REJECTED: honoured when `now < deadline + grace`, EXPIRED otherwise.
   - If the guardrails section is unavailable, use the default 24 h. Keep the processed/late-edit/tamper logic unchanged.
3. Store the grace on the pending decision so that a later config edit cannot reopen it. Either write `deadline + grace` into a second trusted INTERVENTION_LOG column (for example `approval_grace_until`, added in V009 or a new migration), or pass the current run's pinned value. The first is preferred. Update the module docstring: drop the "known limitation", describe the grace, and fix the stale `queue_rows` name (→ `approval_row`).
4. Tests in `tests/integration/test_approval_lifecycle.py`:
   - New test: approve a row at roughly deadline − 2 h, then call `process(now=deadline + ~22 h)` (or run the next cycle with that time). Expect exactly one outbox row and `approval_status = APPROVED`.
   - `test_expired_after_expiry_no_outbox`: unanswered rows still expire at +73 h. The "answered late" case must now be processed after `deadline + grace` (for example +97 h) to expect EXPIRED.
   - Keep `test_edited_expiry_and_backdated_decision_cannot_defeat_deadline`, processed after deadline + grace.
   - Add a unit check that `approval_grace_h` is parsed and validated (a negative value means the guardrails section is invalid).
5. All ten T14 acceptance tests and the full suite must still pass, and ruff must stay clean.
